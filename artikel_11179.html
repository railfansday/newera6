When you click a button and nothing appears to happen, a brief pause later makes the page respond.

People don’t report this as a bug, but they tend to feel more frustrated than when they arrived. This tiny pause is precisely what the Interaction to Next Paint (INP) metric was designed to measure. Since it replaced First Input Delay as a Core Web Vital in March 2024, it has become one of the most challenging metrics for many development teams to address.

Unlike Large Contentful Paint and Cumulative Layout Shift, which can often be improved with image optimizations and reserved boxes, INP is deeply connected to your JavaScript, event handlers, and rendering pipeline.

This guide explains how to identify the interactions that cause delays and the actual fixes that produce real change.

INP observes every click, tap, and key press during a visit and reports the slowest one.

It measures the time between the user’s input and the browser rendering the next frame. On pages with many interactions, one extreme outlier is ignored.

Google’s performance thresholds are straightforward: 200 milliseconds or less is excellent, 200 to 500 milliseconds needs improvement, and anything over 500 milliseconds is poor.

These thresholds are based on the 75th percentile of real user visits, so performance on a fast laptop doesn’t tell the full story. Instead, the slow phone on a poor connection is what matters.

Each interaction is broken into three separate parts:

• Input delay: the time before the event handler can start, usually because the main thread is occupied with another task.

• Processing time: the time the event handler takes to run.

• Presentation delay: the time the browser spends recalculating styles, laying out the page, and painting.

Understanding which part of the interaction is causing the slowdown helps save time and effort, since each part can be addressed differently.

Lab-based tools like Lighthouse cannot interact with a site the way actual users do, so they may miss INP issues entirely.

It’s better to begin with real-user data. The Chrome UX Report and the Core Web Vitals report in Search Console can show you whether there are problems, and on which URLs.

Fix 4: Keep Third-Party Scripts on a Leash

Tag managers, chat widgets, A/B testing tools, and ad scripts all compete for the same main thread as your code.

These scripts are a major cause of high input delay. Since you don't control their code, the main fix is usually about when they load, not how they work.

Load them using a sync or defer, delay non-essential scripts until after the first user interaction or during the page's idle time, and regularly audit them.

It's surprisingly common to find scripts that were added for a campaign years ago and are no longer needed. Removing such widgets can significantly improve performance.
